### D-1 本期是否只上裸 DuckDB、不上 DuckLake

| 选项 | 换来什么 | 代价 |
| --- | --- | --- |
| A. 只上裸 DuckDB 单文件（建议） | 单库文件、无守护进程、无子进程、无额外 catalog；写入最快（实测 8.5ms/次） | 没有版本分支/时间旅行 |

### D-2 AI 接入形态（前提已更正 + D5 实测）

**前提更正（2026-09-27）：** 本节原文的前提是"MotherDuck 是云服务、与'无服务'冲突"——**这条作废**。
MCP 用的是官方**本地**包 `mcp-server-motherduck`：自托管程序，可连本地 duckdb 文件 / 内存库 / S3，
**不经过 MotherDuck 云**；云端方案不在本期范围。本期真正的约束是 **DuckDB 的独占文件锁**（实测见下）。

| 选项 | 说明 |
| --- | --- |
| A. 应用自己的 HTTP 出口（建议） | 零新增开库进程，直接复用现有权限/软删除语义；AI 与 Web 走同一条已验证的链 |
| B. 本地 MCP 直连活库 | 官方本地包、自托管、不经云；但它是**另一个进程开同一个库文件**，应用持有常驻连接时查不动（实测），反向亦然。应用改成**按请求开关 + 两端退避重试**后可行，见 D5-b |
| C. MCP 只读"应用导出的快照副本" | 不与活库抢锁；代价是数据滞后一个导出周期，且导出必须由应用进程自己做 |

**建议：A**（任意 SQL 分析诉求出现时按 C 补快照），**D5 实测支持这个建议**：

- 应用持 rw 常驻连接时，第二个进程开同一文件**一律失败在 open 阶段**（3–8ms，不重试）：`rw` / `read_only=True` /
  `ATTACH ... (READ_ONLY)` / `lock_configuration=false` 四种写法全部报
  `IO Error: Could not set lock on file "...": Conflicting lock is held in ... (PID)`。
- 锁在**连接关闭**那一刻释放，不必等进程退出（应用 close → 第二个进程立刻能开；应用重开 → 立刻又被独占）；
  "排队等待"**DuckDB 不内置**：每秒重试 5 次全失败；只有当对方真的放锁时重试才有用（应用 4 秒后放锁 → 第 5 次成功）。
- 官方 MCP 实测（应用持常驻连接的前提下）：进程起得来、`initialize` / `tools/list` 都成功，**失败在真正的工具调用**，
  报同一个 `IOException`；`--read-write`、`--ephemeral-connections` 都不改变这一点。
- 反向也成立：MCP 持连接期间（常驻读写，或 `--no-ephemeral-connections` 的常驻只读），应用侧开库直接失败。
- **sqlite 对照**：WAL 下第二个进程**读**不受影响；**写**拿不到锁时会**排队**——应用 3s 后提交，第二个进程
  busy_timeout=5s 等到 3.0s 后成功；应用一直不放，busy_timeout=1s 就在 1.0s 失败、busy_timeout=0 则 0.2ms 立刻失败。
  即"Sylens 说的 sqlite + MCP 同理"**只对了一半**：sqlite 的"排队等一会儿"能做到，DuckDB 做不到
  （sqlite 锁按事务粒度且 WAL 允许多读，DuckDB 锁是文件/进程级、开库即占）。

实测命令与原始日志：`pixi run lock-spike`、`pixi run lock-forms`，
输出留档在 `spikes/duckdb_lock/logs/`（脚本在 `spikes/duckdb_lock/`，可原样复跑）。

### D-2 补充实测（D5-b）：按请求 open/close 时这套能不能成立

技术组长指出：**"锁一直被持有"是当前连接池写法的产物**（`server/db.py` 的 `create_engine` 用默认池，
连接用完整条放回池里、文件句柄不关），不是 DuckDB 的要求。这条实测**成立**，并且改变了 D-2 的结论边界。

实测证据（`pixi run lock-per-request`，日志 `spikes/duckdb_lock/logs/lock-per-request.log`）：

| 场景 | 实测结果 |
| --- | --- |
| 同进程对比池形态 | `NullPool`（每请求开关）7.2ms/次、用完 `/proc/self/fd` 里**没有**库文件句柄；常驻池（StaticPool，当前形状）0.22ms/次、fd **一直挂着** |
| 应用按请求开关（每请求持锁 ~15ms、间隙 60–85ms，锁占用 14–29%）+ 外部进程（不重试） | 369–400 次尝试成功 62.5–66.4%，失败都是同一个 lock `IOException`，~7ms 内返回 |
| 同上 + 官方 MCP 真跑一个会话（20 次 `execute_query`） | 成功 17–19/20（85–95%）；应用**常驻**连接的对照是 0/3 |
| 应用自己不重试 | 80 个请求里丢了 19 个（对方持锁时应用也开不了库）——是**双向**的 |
| 反向：MCP `--no-ephemeral-connections`（常驻只读） | MCP 存活期间前端写请求 **3/3 全部失败**（只读连接同样挡写）；MCP 退出后立刻恢复 |
| 反向：MCP 默认（ephemeral，查完即放） | MCP 存活期间前端写请求 3/3 成功 |
| 两端都退避重试 | **0 报错**：应用 60 请求 0 失败（内部重试 16–31 次），外部 158–194 次尝试 0 失败；代价见下 |

**MCP 自身是常驻还是按查询开关（源码 + `/proc/<pid>/fd` 双向确认）：**
本地只读文件默认走 `ephemeral_connections=True`——**每次查询新开连接、查完即关**（实测查询后 MCP 进程里没有库文件 fd，
别的进程能正常开库）；只有 `--no-ephemeral-connections` 或 `--read-write` 才会变成**常驻连接**
（实测 fd 8 一直挂着库文件，此时别的进程开不了库）。所以给 AI 用时必须固定成"**默认只读 + ephemeral**"，
绝不能开 `--read-write` 或 `--no-ephemeral-connections`。

**代价（按请求开关 + 两端重试的实测数字）：**

- 每个应用请求多付一次 open/close：NullPool 7.2ms vs 常驻 0.22ms（轻接口 ≈ +7ms）。
- 撞锁的那次请求要等到对面放锁：应用请求 p95 从 ~30–43ms 涨到 ~133ms（max 214ms）；外部查询 p95 70–127ms（max 1010ms）。
- **重试逻辑该落在哪一层**：应用侧落在 `server/db.py` 的 `session()`/引擎层（捕 `IOException: Could not set lock` 退避重试）
  并把池换成 `NullPool`；MCP 侧 `mcp-server-motherduck` **没有重试开关**，错误直接作为 tool error 返回，
  只能由 MCP 客户端/agent 侧重试——那部分不在我们手里，客户端不重试就会把这次报错显示给用户。
- D2（并发与一致性加固）的范围要相应扩大：除了原本的"同进程写冲突重试 + 单实例保护"，
  还要加"**锁获取退避重试**"和"**连接池改 `NullPool`**"。

三种绕锁形态的实测成本与新鲜度（20,000 batches + 60,000 file_versions 的合成活库）：

| 形态 | 谁在什么进程里开库 | 数据从哪来 | 滞后 | 实测成本 | 主要风险 |
| --- | --- | --- | --- | --- | --- |
| (i) 快照副本 | 应用进程内导出；MCP 只读那份快照 | 应用定期导出的 parquet 目录 / 只读 duckdb 文件 | = 触发间隔（5 分钟一次 → 最多 300s） | parquet 导出 16–19ms / 1.1MB；只读 duckdb 快照 124–136ms / 1.5MB；快照被独立进程打开 9ms | 第二个进程**自己导不了**（实测 open 即失败），必须由应用进程内的定时任务/管理端点触发；数据有滞后 |
| (ii) 应用 HTTP 出口 | 只有应用进程开库 | 现有 API | ≈0（同库实时） | `GET /api/projects` 1.8ms、`/api/batches?project_id=1` 56ms（111.8KB）、`/api/trash` 3ms | 取数是"按接口粒度"，任意 SQL 分析要新加只读查询接口 |
| (iii) 按需 open/close | 应用每个请求开/关连接 | 同库，但请求间隙库是"无人持有"的 | ≈0 | 单次 open+查询+close 6.9–7.2ms（常驻连接 0.18ms，每请求多付约 6.8ms） | 应用松手的窗口里**外部进程可以抢到锁**，应用下一个请求直接失败（实测，直到外部进程退出才恢复）；多线程下还要全局串行化 |

**推荐形态（写清到进程/数据来源/滞后）：**

1. **首选 (ii)**：MCP 不直接开库，AI 走应用自己的进程——应用进程是唯一持有 DuckDB 文件锁的进程，
   数据来自活库、滞后 0；现有 `require_user` / `require_manager` 与 `deleted_at IS NULL` 软删除语义直接复用。
   需要补的是"给 AI 的只读查询接口"（若要任意 SQL，则限定 SELECT + 行数上限 + 超时）。
2. **需要任意 SQL 分析时用 (i)**：应用进程内定时 `EXPORT DATABASE`（16ms 级）或导出一份只读快照文件，
   MCP 只读那份；滞后等于触发间隔（5 分钟一次 → 最多 300s），必须由应用自己触发。
3. **(iii) 不作为常规形态**：它能真释放锁，但代价是每请求 +7ms、以及"关着的时候被别人抢走锁"的偶发失败；
   只适合停机维护窗口这类"可以确定没有别的开库者"的场景。

**D5-b 之后要补一句（按请求开关 + 两端重试）：** 如果按请求 open/close（`NullPool`）**并且两端都退避重试**，
AI 直连活库**是能成立的**（实测 0 报错）——前提是：① 应用池换 `NullPool` 且 `session()` 层加锁获取重试；
② MCP 固定"默认只读 + ephemeral"（不能 `--read-write` / `--no-ephemeral-connections`）；
③ 接受偶发百毫秒级延迟抖动，以及"MCP 客户端不重试时会看到一次报错"（MCP 自身没有重试开关）。
这与选项 B（直连活库）是同一件事，只是把"不可行"改判为"有条件的可行"。

**结论：待确认（建议 A 为主线；若 Sylens 要 AI 侧任意 SQL，B 在有上述前提下可选，见 D5-b）。**

## 三、已定结论：自增主键按后端分支（P0 预研）

评估给的方向是"用 `Sequence` 写法统一三后端"，实测**走不通**：sqlite 编不出 DDL、seekdb 编成非法
DDL、DuckDB 又不认 `autoincrement`。所以 D1 必须按后端分支。

脚本：`spikes/pk_autoincrement_spike.py`，`pixi run pk-spike`。断言方式是真建表、真插入、
真读回 id，并在每个后端把两种写法都跑一遍形成对照矩阵。

实测矩阵（`ok` = `create_all` 成功且能取回自增 id）：

| 后端 | `autoincrement=True` | `Sequence(...) + server_default=seq.next_value()` |
| --- | --- | --- |
| sqlite | **ok** | err: `NotImplementedError: Dialect 'sqlite' does not support sequence increments.` |
| seekdb | **ok** | err: `pymysql.err.ProgrammingError (1064, ... near 'nextval(projects_id_seq) ...')` |
| duckdb | err: `CatalogException: Type with name SERIAL does not exist!` | **ok** |

分支写法：

```python
def _pk_column(backend, table):
    if backend == "duckdb":
        seq = Sequence(f"{table}_id_seq")
        return Column(Integer, seq, primary_key=True, server_default=seq.next_value())
    return Column(Integer, primary_key=True, autoincrement=True)
```

三后端跑通记录（父表 projects + 带外键的子表 batches，与真实形状一致）：

```
=== sqlite（分支写法：autoincrement）===
  [分支写法] autoincrement  ok   前两条 id=[1, 2] 子表 id=1  显式插 id=7 后下一行 id=8
  [统一写法] sequence       FAIL -> NotImplementedError: Dialect 'sqlite' does not support sequence increments.

=== seekdb（分支写法：autoincrement）===
  [分支写法] autoincrement  ok   前两条 id=[1, 2] 子表 id=1  显式插 id=7 后下一行 id=8
  [统一写法] sequence       FAIL -> ProgrammingError: (1064, "You have an error in your SQL syntax ... near 'nextval(projects_id_seq) ...'")

=== duckdb（分支写法：sequence）===
  [统一写法] autoincrement  FAIL -> ProgrammingError: (_duckdb.CatalogException) Catalog Error: Type with name SERIAL does not exist!
  [分支写法] sequence       ok   前两条 id=[1, 2] 子表 id=1  显式插 id=7 后下一行 id=3
           └ 落库 id=[1, 2, 3, 7]：序列不跟随显式 id，D3 必须 restart
```

环境：duckdb 1.5.5 / duckdb-engine 0.17.0 / SQLAlchemy 2.0.50 / Python 3.14。

**给 D1 的落点**：分支放在 `server/models.py`（现有的 `with_variant` 只能表达类型，表达不了主键定义）；
`duckdb`、`duckdb-engine` 已进 `pixi.toml` / `pixi.lock`，D1 直接复用。

**给 D3 的落点**：duckdb 的序列**不跟随**显式插入的 id——实测插完 `id=7` 后序列仍停在 3，
下一行拿到 `id=3`。迁移收尾必须把每张表的序列 `restart` 到 `max(id)+1`，否则第一条新数据就会撞主键。

## 四、风险清单（按重要性）

1. **跨进程独占锁（D5 实测确认）**：只要一个进程以读写打开 DuckDB 文件，第二个进程连只读都打不开
   （rw / read_only / `ATTACH ... (READ_ONLY)` / `lock_configuration=false` 四种全部
   `IO Error: Could not set lock on file`，3–8ms 内失败、不重试）。
   双开实例、AI/MCP 另进程读库、DBeaver/Excel 直连外部工具全部受限。架构决定，只能靠"AI 走应用接口"规避。
   反向同样成立：外部进程（含 MCP）持连接时，应用也开不了库。
2. **同进程写冲突**：两个线程同时更新同一行时 DuckDB 直接抛 `Conflict on update!`（sqlite/seekdb 是等待或重试），
   `session()` 没有重试就会偶发 500——D2 收口。
3. **模型层必须按后端分支**：三后端无法统一，测试基座同进程切后端那条路（`tests/test_migration.py`）要跟着改。
4. **DuckLake 是额外复杂度**：不解决并发，还多 catalog + 快照/压缩运维 + 约 4 倍写开销。
5. **MCP 的真约束是文件锁，不是云**（D5 更正）：`mcp-server-motherduck` 是自托管本地包、不经云，
   但它是另一个进程开同一个库文件——应用在跑时 MCP 的工具调用直接报同一个锁错误（实测），反向亦然。
6. **分析型引擎当 OLTP 用**：行级更新内部是 delete+insert，长期需要 checkpoint/压缩。当前数据量没问题。
7. **duckdb-engine 是社区方言**（非 SQLAlchemy 官方），版本耦合需留意。
8. **备份方式变了**：不能拷活文件（有 WAL），要应用内 checkpoint/导出——D2 收口。
