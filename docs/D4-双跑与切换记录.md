## 3. 双跑：真实流程 + 逐接口比对

同一份探针脚本对两个后端各跑一遍（`spikes/d4/dual_run_probe.py probe`），覆盖
建项目/批次、上传、下载（比对返回字节的 sha256）、改批次备注、删文件/批次/项目、
回收站、恢复，以及唯一性 409 用例：

| 后端 | 调用数 | 5xx | 状态码序列 |
| --- | --- | --- | --- |
| sqlite（基线） | 24 | 0 | 登录 200 … 重名项目/批次 409，末条大小写不同 201 |
| ducklake | 24 | 0 | 与基线完全一致 |

比对口径：时间戳归一成 `<TS>`；`/api/file-config` 的 `file_fields` 来自 config 里的
`set`，顺序随 `PYTHONHASHSEED` 变（同一后端重跑也会变，与后端无关），排序后比对。

结果：**24 个接口归一化后逐字节一致**，且新建记录拿到的 id 也相同
（项目 5 / 批次 13 / 文件 7），说明 id 计数器 restart 到位、两后端分配行为一致。
服务日志无 `Failed to commit DuckLake`、无 `already exists`、无 `database is locked`。

回归测试：

| 命令 | 结果 |
| --- | --- |
| `pixi run test` | 145 passed / 20 skipped |
| `LABFLOW_DB=ducklake pixi run test` | 164 passed / 1 skipped |

## 5. 回滚演练

动作就是切回 `LABFLOW_DB`（D4 不做数据反向回迁）：

```bash
# deploy/labflow.env: LABFLOW_DB=ducklake  →  LABFLOW_DB=sqlite
pixi run serve
```

| 项 | 结果 |
| --- | --- |
| 服务启动 | 正常，`http://127.0.0.1:9002` |
| 登录 | `leader` 200 |
| 读到冻结点数据 | 活跃项目 3、活跃批次 7、回收站 项目 1 / 批次 5 / 文件 2 |
| 冻结点是否被写 | 否（4 表校验和与第 1 节完全一致） |

**注意**：回滚回的是冻结点，切换后在 DuckLake 侧新增的数据不会出现在 sqlite 里
（本演练未产生真实生产写入）。若要保住切换后的写入，需用切换后的 DuckLake 备份人工
补录，或反向迁移——这是"回滚有损"的已知边界，触发回滚前先确认能否接受。

## 6. 观察清单

切换后（DuckLake 为生产、sqlite 冻结为回滚点）要盯的项：

| 指标 | 怎么看 | 阈值 / 触发 | 负责人 |
| --- | --- | --- | --- |
| 5xx | 服务日志 / 前端报错 | 出现无法靠重试自愈的 5xx | 值班/负责人 |
| 数据一致性 | 每日跑 `spikes/d4/backend_digest.py ducklake data/ducklake` 与前一日对账 | 行数或校验和异常变化 | 值班/负责人 |
| catalog / ATTACH 异常 | 日志 grep `Failed to commit DuckLake`、`already exists`、`database is locked`、`DATA_PATH` | 频繁出现或导致请求失败 | 值班/负责人 |
| 唯一性假阳性 | 库里没有同名，却返回 409 | 反复出现 | 值班/负责人 |
| id 重号 | 新记录 id 是否与历史冲突 | 出现重号 | 值班/负责人 |
| 备份可用性 | 每日备份 + 每周还原演练 | 连续 2 天备份失败 | 值班/负责人 |
| 磁盘增长 | `data/ducklake` 与 parquet 体积 | 异常膨胀（缺 compaction） | 值班/负责人 |

回滚触发条件（满足任一即执行第 5 节回滚动作）：

1. 出现靠应用层退避重试也救不回来的 5xx，且定位到 DuckLake/catalog。
2. 数据一致性对账不通过（行数/校验和异常、重名或重号入库）。
3. ATTACH/catalog 故障导致服务起不来，短时间无法恢复。
4. 备份连续失败超过 2 天（回滚点随时可能失效）。

按需求，"连续一周无 5xx"这类观察由人/值班执行，agent 不等：以上基线与清单即为交付。

## 7. 回滚窗口与建议

- **回滚窗口**：2–4 周，自切换时刻 **2026-09-28** 起算，即 **2026-10-12 ~ 2026-10-26**。
  窗口内保留：冻结的 `data/labflow.db`（只读）、`uploads/` 冻结点副本、切换后的
  DuckLake 备份。
- **建议**：窗口内先按观察清单盯指标；无异常则在窗口结束前把 `LABFLOW_DB` 定为
  `ducklake`、并按既定备份策略退出回滚窗（届时 sqlite 冻结点可归档）。

## 8. 复现方式

```bash
# 1. 起服务（示例端口 9101），造一份代表性数据
LABFLOW_DB=sqlite LABFLOW_PORT=9101 pixi run python server.py &
pixi run python spikes/d4/dual_run_probe.py seed  --base-url http://127.0.0.1:9101 --out seed.json

# 2. 冻结点：记录并保存 data/labflow.db + uploads/
pixi run python spikes/d4/backend_digest.py sqlite data/labflow.db

# 3. 迁移 + 独立核对
pixi run migrate-ducklake
pixi run python spikes/d4/backend_digest.py ducklake data/ducklake

# 4. 双跑（deploy/labflow.env 切 ducklake 后起服务）
pixi run python spikes/d4/dual_run_probe.py probe --base-url http://127.0.0.1:9002 --out ducklake.json

# 5. 备份 + 还原演练
pixi run backup
pixi run restore backups/<时间戳> <新目录>
```
