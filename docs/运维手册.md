# LabFlow 部署与运维手册

面向使用者的操作手册：怎么部署、怎么启动、怎么备份、怎么回滚。所有命令都在
仓库根目录执行，环境一律走 pixi。

## 1. 环境要求

- Linux 服务器（x86_64），systemd 可用。
- 已安装 [pixi](https://pixi.sh)（`pixi --version` 能打印版本）。
- 仓库已 `git clone` 到服务器上，例如 `/opt/LabFlow`。
- 局域网内其他电脑能访问服务器 IP。

依赖、脚本、运行环境全部由 `pixi.toml` / `pixi.lock` 管理，不要用 pip / npm / conda
绕过 pixi。

## 2. 首次部署

```bash
cd /opt/LabFlow
pixi install --frozen          # 按 pixi.lock 装好环境
```

检查运行配置 `deploy/labflow.env`（systemd 服务与 `pixi run serve` 都读它）：

```text
LABFLOW_DB=seekdb        # 后端：seekdb / ducklake / sqlite（回滚用）
LABFLOW_PORT=9002        # 监听端口，须与 server/config.py 默认值一致
LABFLOW_BASE_PATH=       # 子路径前缀，留空即挂在根路径
LABFLOW_KEEP_BACKUPS=14  # 备份保留份数
```

安装开机自启服务：

```bash
sudo pixi run service-install
```

该命令会渲染 `deploy/labflow.service.template` 到
`/etc/systemd/system/labflow.service`，`daemon-reload`、`enable`、`start`，
替代旧的 Windows 自启脚本（`启动LabFlow.bat` / `LabFlow_AutoStart.vbs` 已删除）。

> 首次切到 seekdb 前，确认已经跑过数据迁移（P3 的 sqlite → seekdb 脚本），否则
> 空库会看起来“没有数据”。迁移完成前可以先保持 `LABFLOW_DB=sqlite`。

迁移脚本（`pixi run migrate-seekdb`）的退出码：`0` 成功、`1` 校验不一致、
`2` 预检失败、`3` 目标库非空被拒。预检失败包含源库结构漂移（源库带着
`server/models.py` 里已移除的历史列）：这种情况一行都不会写进目标库，把模型与源库
对齐后直接重跑即可，不需要手工清库。

## 3. 日常启动 / 停止 / 查看

```bash
systemctl status labflow          # 查看状态
sudo systemctl restart labflow    # 重启
sudo systemctl stop labflow       # 停止
sudo systemctl start labflow      # 启动
journalctl -u labflow -f          # 跟踪日志
```

调试时前台运行（Ctrl+C 停止）：

```bash
pixi run serve
```

访问地址：

```bash
hostname -I            # 取第一个 IP，形如 192.168.x.x
```

```text
服务器本机：http://127.0.0.1:9002
局域网其他电脑：http://<服务器IP>:9002
```

其他电脑打不开时，确认服务器防火墙放行了 TCP `9002`：

```bash
sudo ufw allow 9002/tcp
# 或
sudo firewall-cmd --add-port=9002/tcp --permanent && sudo firewall-cmd --reload
```

## 4. 备份

备份按当前后端自动选路，产物都是一份带校验清单的备份目录：

| 后端 | 做法 | 要不要停服 |
| --- | --- | --- |
| `ducklake` | 停服拷贝整个 `data/ducklake/`（DuckDB/DuckLake 有 WAL，**不能拷活文件**） | 是，秒级：脚本自动停服、拷完自动起回来 |
| `sqlite` | `VACUUM INTO` 一致性快照（在线安全） | 否 |
| `seekdb` | `seekdb-dump` 导出（在线安全） | 否 |

```bash
pixi run backup                 # 备份到 backups/labflow-<时间戳>/
pixi run backup /mnt/backup     # 也可以指定别的备份根目录
```

后端取 `deploy/labflow.env` 里的 `LABFLOW_DB`（命令行环境变量优先），不需要手工指定。

每份备份目录里有：

| 文件 | 内容 |
| --- | --- |
| `ducklake/` | DuckLake 目录整份拷贝（`catalog.sqlite` + `data/` + `ids.sqlite`） |
| `labflow.sql` | `seekdb-dump` 导出的数据库 SQL |
| `labflow.db` | sqlite 一致性快照（或 seekdb 备份里附带的回滚点） |
| `uploads.tar.gz` | 上传文件打包 |
| `row-counts.json` | 各表行数，供还原时校验 |
| `manifest.txt` | 备份时间、后端、数据目录（还原脚本据此选路） |
| `SHA256SUMS` | 校验和 |

保留份数由 `LABFLOW_KEEP_BACKUPS` 控制（默认 14），超出后自动清理最早的备份。

建议加一条定时任务，例如每天凌晨 2 点备份：

```bash
0 2 * * * cd /opt/LabFlow && pixi run backup >> /var/log/labflow-backup.log 2>&1
```

> **ducklake 后端下备份会短暂停服。** DuckDB 是进程独占锁、DuckLake 又带 WAL，活拷
> 可能拿到旧数据或半个状态。脚本会 `systemctl stop labflow` → 确认没有进程还占着库
> （`deploy/verify_ducklake.py probe-unlocked`）→ 整目录拷贝 → 自动起回来，并在副本上
> 记一次行数。如果服务不是 systemd 起的（比如前台 `pixi run serve`），脚本会拒绝拷贝并
> 提示先停掉它——这是有意设计，不要绕过。

## 5. 还原验证（演练）

备份是否真的能用，靠还原演练证明。还原只写目标目录，不动线上数据：

```bash
pixi run restore backups/labflow-20260928-020000 /tmp/labflow-restore
```

脚本读备份里的 `manifest.txt` 自动选路：

| 后端 | 还原到 |
| --- | --- |
| `ducklake` | `/tmp/labflow-restore/data/ducklake` |
| `sqlite` | `/tmp/labflow-restore/data/labflow.db` |
| `seekdb` | `/tmp/labflow-restore/data/seekdb` |

上传文件统一解到 `/tmp/labflow-restore/uploads`，然后逐表比对行数；行数不一致会以非零
退出码报错。

DuckLake 目录可以整体搬走：应用挂载时带了 `OVERRIDE_DATA_PATH`，所以还原到别的目录也能
直接跑（catalog 里记的旧数据路径不会挡住）。

确认无误后，演练目录可以删掉。真正做灾难恢复时，把还原出的 `data/` 和 `uploads/`
放回仓库目录，再重启服务即可。

## 6. 回滚到 sqlite

seekdb 上线后，sqlite 冻结为只读回滚点，保留 2–4 周。需要回滚时：

### 6.1 准备回滚点

在切换 seekdb 之前，把当时的 sqlite 库另存一份：

```bash
mkdir -p backups
cp data/labflow.db backups/sqlite-frozen-$(date +%F).db
```

### 6.2 执行回滚

```bash
sudo pixi run rollback-sqlite                                   # 自动取最新的 sqlite 快照
sudo pixi run rollback-sqlite backups/sqlite-frozen-2026-09-23.db   # 或指定快照
```

脚本按顺序做四件事：

1. 停止 `labflow` 服务；
2. 把当前 seekdb **完整备份一份**（回滚不会丢切换后的新数据）；
3. 用 sqlite 快照覆盖 `data/labflow.db`；
4. 把 `deploy/labflow.env` 的 `LABFLOW_DB` 改成 `sqlite` 并重启服务。

回滚后 sqlite 重新成为线上库。切换期间写入 seekdb 的数据在上一步生成的备份目录里，
如需找回可按第 5 节还原后人工处理。

## 7. 卸载

```bash
sudo pixi run service-uninstall    # 停服务、关自启、删 unit，不动数据
```

## 8. 故障排查

| 现象 | 排查 |
| --- | --- |
| `systemctl status labflow` 显示 failed | `journalctl -u labflow -n 100` 看报错 |
| 其他电脑打不开 | 防火墙是否放行 `9002`；`hostname -I` 确认 IP |
| 页面能开但没数据 | `deploy/labflow.env` 的 `LABFLOW_DB` 是否指对了后端；迁移是否跑过 |
| 端口被占用 | `ss -ltnp \| grep 9002`，改 `LABFLOW_PORT` 后 `sudo systemctl restart labflow` |
| 备份报找不到 `data/seekdb` | 服务是否已用 `LABFLOW_DB=seekdb` 启动过 |
| 备份报“DuckLake 目录仍被占用” | ducklake 后端必须停服拷贝；先 `systemctl stop labflow`（前台跑的 `pixi run serve` 就 Ctrl+C），别绕过这条检查 |
| 日志里偶发 `Failed to commit DuckLake transaction ... database is locked` | catalog 是 SQLite 单写者，两个事务同时提交时后者会撞；应用侧 `session()` 已做退避重试（3 次以内基本都成功）。若仍频繁出现，多半是有第二个写进程（双开实例、或 MCP 用了读写模式），停掉多余的写进程 |
| 日志里 `database with name "dlk" already exists` | 连接层把 DuckLake 又 ATTACH 了一次；正常实现是“每进程 ATTACH 一次、池内复用”，出现说明有旁路代码自己 ATTACH，去掉它 |
| 报 `DATA_PATH ... does not match` 或提示要 `OVERRIDE_DATA_PATH` | DuckLake 目录被搬到了别的路径。应用与 `deploy/verify_ducklake.py` 都带了 `OVERRIDE_DATA_PATH`，报这个的多半是外部工具（例如本地 MCP）自己 attach 的，给它加 `OVERRIDE_DATA_PATH true` |
| 双开实例 / AI 想直连活库 | DuckDB 是进程独占锁（D5/DL1 实测：第二个进程连只读都打不开）。AI 走应用接口，或用只读方式 attach DuckLake catalog 读活库 |
